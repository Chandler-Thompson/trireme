# Documentation

- **Module:** documentation
- **Version:** 2
- **Governs:** where project documentation lives and who may change what.
- **Depends on:** communication, journal.
- **Settings:** none yet.

## One place

All of a project's documentation lives **in the project repo under `docs/`**, so it moves
with the code it describes and every seat can reach it under any harness. Docs are code:
they are reviewed and merged like code. API references are generated from the code, never
written by hand.

```
docs/
  PRD.md                 intent; only the user changes it
  architecture.md        the architecture doc
  adr/                   architecture decision records
  performance.md         hot paths and their benchmarks
  standards.md           the project's effective standards (generated, see below)
  <seat>/                one folder per staffed seat, holding what its role file lists
```

## Two sources of truth

**The PRD says how things should be. The code says how things are.** Every other document
defers to those two. Where a document disagrees with either, the document is wrong and
gets fixed.

## The PRD

- **Only the user updates it**, through the application's PRD editor or by any other
  means they choose.
- Seats with questions, comments or concerns may come up with a solution, implement it
  and test it on a branch, then bring it to the user. It can reach `develop` flagged as a
  PRD deviation, and cannot enter a release without the user's approval
  (`modules/version-control/`).
- A PRD written by the Producer or drafted by the XO is marked **"PRD generated by AI"**
  until the user accepts or edits it. From then on it is the user's alone to change.

## The architecture doc

- Written by **all the Engineer seats working together**. It is complete when every
  staffed Engineer seat has been consulted and has approved it.
- **Every later change needs full re-approval** from every staffed Engineer seat, so
  security, analytics, QA and the rest are not left behind by a last-minute change.
- If one seat keeps raising concerns, the Technical Lead rules, based on the project's
  goals and everyone's input, and logs the ruling for the user's review.
- Hot paths are kept out of it, in `docs/performance.md`, so declaring one does not
  trigger a full re-approval. The architecture doc links to it.

## ADRs

The Technical Lead writes one only when a decision is hard to reverse, would surprise
someone without the context, and came from a real trade-off. Each ADR gets a plain-language
summary for the user.

## The standards file

The project's standards live in the instance's settings: the doctrine's standards
module, the chosen profile and the project's deviations (`modules/standards/`). The
application writes the effective result to `docs/standards.md` so every seat can read it
in the repo. That file is generated, marked as generated, and never edited by hand.
